> The `sales.*` and `receipts.*` preload-bridge namespaces are the
> **trust boundary** between the renderer and the main process for
> sale-finalization and receipt operations (Constitution §III;
> plan AD-1). Every handler in this contract is gated at the bridge
> surface — renderer-side checks are secondary UX defence only and
> are NEVER load-bearing.
>
> **There is no `drawer.*` renderer-callable surface.** The drawer
> kick is a consequence of a successful print on a cash-inclusive
> sale, issued by the main-process print pipeline (per spec FR-040
> and plan AD-5 / AD-8). Renderer observes drawer state via the
> `sales.subscribe` payload (which includes the latest DrawerEvent).
>
> **This contract is DRAFT.** It defines the typed seam that the
> renderer and the main process MUST compile against once Slice 1
> is authorised. **No code is authored by this file.**
> `/speckit-tasks` produces the implementation tasks per slice.

## Bridge gating — `requireOperatorSession`

Every handler in the `sales.*` and `receipts.*` namespaces MUST
begin with:

```text
const session = requireOperatorSession({
  role?: 'cashier' | 'manager' | 'admin',
  sale_id?: string,
})
```

The helper is the same one 004 / 005 / 006 use; 008 reuses it,
not re-implements it. Failure modes (mirrors 006's gating
pattern):

| Condition | Result |
|:--|:--|
| No active session | `{ kind: 'refused', reason: 'no_session' }` per 004 FR-005 / FR-016. |
| Wrong role for this handler | `{ kind: 'refused', reason: 'role_denied' }` (008 v1: no handlers require a non-cashier role per AD-10, but the gate exists for future expansion). |
| Tenant / branch / terminal mismatch between session and sale | `{ kind: 'refused', reason: 'tenant_isolation' }`. |
| `sale_id` given but the sale does not exist (or is not visible to this terminal's tenant scope) | `{ kind: 'refused', reason: 'sale_not_found' }`. |

**All refusals use generic wording.** No factor-distinguishing
variants (004 NFR-003 inherited; spec FR-006 / FR-022). The refusal
`reason` lives in the bridge payload for diagnostic logging (with
redaction); it is NOT echoed to the cashier as-is — the renderer
translates each reason to a generic "this action isn't allowed
right now" UX. See [../research.md](../research.md) R-5 for the
`reason` vs `category` reconciliation inherited from 006.

## Idempotency — `idempotency_key` (UUID v4)

Every **mutating** handler in `receipts.*` accepts an
`idempotency_key: string` (UUID v4) generated by the renderer at
the moment of intent. The bridge handler (mirrors 005 / 006's
idempotency contract):

1. Looks up the relevant event table by `idempotency_key`.
2. If found AND the payload hash matches: no-op; returns the
   original outcome (Constitution §P5).
3. If found AND the payload hash differs: refuses with
   `{ kind: 'refused', reason: 'idempotency_payload_mismatch' }`.
4. If not found: applies the action AND writes the event row in the
   same SQLite transaction.

The renderer MUST NOT generate a new `idempotency_key` on retry —
the same UUID must accompany every retry of the same intended
operation.

**`sales.*` is read-only**; no `idempotency_key` parameter on its
handlers.

## Refusal envelope

Every refused response from any `sales.*` or `receipts.*` handler
is shaped:

```text
{ kind: 'refused', reason: <closed enum> }
```

The closed enum across all 008 handlers:

| `reason` | Meaning |
|:--|:--|
| `no_session` | No active operator session (gate failure). |
| `role_denied` | Wrong role for this handler. |
| `tenant_isolation` | Session's tenant/branch/terminal does not match the sale's. |
| `sale_not_found` | The `sale_id` does not exist or is out of scope. |
| `not_yet_printed` | Reprint refused because no prior successful PrintEvent exists for this sale. |
| `idempotency_payload_mismatch` | Same key, different payload. |
| `printer_unavailable` | Print refused at the bridge layer because the printer adapter is not initialised. |
| `forbidden_field_in_request` | Defensive guard — a forbidden field key was detected in the request payload (mirrors the data-model finalize-time forbidden-fields check). |

The renderer maps every reason to **generic** copy (Constitution
P11). No reason-specific user-facing message exists. Per-reason
diagnostic context lives in the audit payload (with the redaction
discipline from plan AD-9).

## Namespace: `sales.*` (read-only)

### `sales.read`

Read a single sale by id.

```text
Request:
  { sale_id: string }

Response (success):
  { kind: 'ok',
    sale: {
      sale_id: string,
      sale_number: string,
      receipt_number: string,
      tenant_id: string,
      branch_id: string,
      terminal_id: string,
      terminal_label: string,
      selling_operator_id: string,
      selling_operator_display_name: string,
      subtotal_minor: number,            // INTEGER minor units
      total_tax_minor: number,           // INTEGER minor units (sale-level VAT)
      total_change_due_minor: number,    // INTEGER minor units
      tender_lines_summary: TenderLineSummary[],
      finalized_at: string,              // ISO-8601 UTC
      latest_print_event?: PrintEventSummary,
      latest_drawer_event?: DrawerEventSummary,
    }
  }

Response (refused):
  { kind: 'refused', reason: <one of the enum above> }
```

**Notes.**

- The response **excludes** the `envelope_handoff_action_id`, the
  `payment_attempt_id`, the `envelope_cart_id`, and the
  `tenant_tax_registration_id` — those are main-process / audit-
  layer fields. The renderer does not need them to render the
  preview UI; if a future renderer feature needs one of them, it
  must be reviewed under §P15 (minimised state to renderer).
- `tender_lines_summary` carries the FR-017 minimum: per-line
  `tender_type` label, `amount_applied_minor`, `change_due_minor`
  (cash only), and optionally the non-sensitive identifiers
  (`external_reference` if 006 OQ-PLAN-5 resolves permissively;
  `voucher_authority_redemption_id` if 006 FR-017 / OQ-PLAN-7
  resolves permissively). NO voucher code, NO PAN, NO any
  sensitive field crosses the bridge to the renderer
  (Constitution §P6 / §P7).
- `latest_print_event` and `latest_drawer_event` are projections:
  the latest row by timestamp. The renderer uses them to drive the
  reprint affordance visibility (AD-10) and the drawer-failure
  banner.

### `sales.findByNumber`

Look up a sale by its cashier-quotable `sale_number` (per AD-7).
Used by the cashier "find sale" workflow when a customer phones in.

```text
Request:
  { sale_number: string }

Response (success):
  { kind: 'ok', sale: <same shape as sales.read> }

Response (refused):
  { kind: 'refused', reason: 'sale_not_found' }
```

**Notes.**

- Tenant-isolation rule: the lookup is scoped to the current
  session's `tenant_id` + `branch_id` + `terminal_id`. A sale on a
  *different terminal* in the same branch is NOT returned — the
  cashier would need to phone-walk through the other terminal.
  This is intentional under Constitution §P17 (tenant isolation is
  terminal-level for support queries).

### `sales.subscribe`

Subscribe to live sale-related state for the current terminal. The
renderer uses this for the preview-on-finalize refresh and for
banner-update events.

```text
Request:
  { topic: 'recent' | 'banner_state' }

Subscription payload (`topic='recent'`):
  Emits on every new `sale.finalized` audit event for the current
  terminal — a compact sale summary (sale_id, sale_number,
  finalized_at) suitable for the cashier's "most recent sale" UI.

Subscription payload (`topic='banner_state'`):
  Emits on every new PrintEvent or DrawerEvent for the current
  terminal — the projected banner state (no banner / printer-
  failure-banner / drawer-failure-banner) suitable for the
  renderer's persistent banner UI.

Unsubscribe semantics:
  Mirrors 005 / 006 `subscribe` handlers — the renderer holds a
  subscription token and explicitly calls `sales.unsubscribe`
  with the token to detach.
```

## Namespace: `receipts.*` (mutating)

Every mutating handler accepts an `idempotency_key: string` (UUID v4).

### `receipts.preview`

Render the preview of the receipt for a given sale.

```text
Request:
  { sale_id: string,
    idempotency_key: string }

Response (success):
  { kind: 'ok',
    preview: {
      // The HTML/canvas rendering of the receipt. The shape is the
      // AD-6 single-source dual-output engine's HTML output. The
      // renderer renders this directly to a preview panel.
      html: string,
      // Layout metadata for the renderer's preview-pane to mirror
      // the printed slip's dimensions.
      width_chars: number,    // ESC/POS column width (e.g., 32 / 48)
      bilingual_locale: 'ar-EG-RTL-with-latin-en' | … ,
    }
  }

Response (refused):
  { kind: 'refused', reason: <one of the enum above> }
```

**Notes.**

- **Does NOT emit a print command.** Preview is renderer-only;
  Constitution Principle IV's loud-failure rule does not apply.
- **Does NOT open the drawer.**
- **Does NOT mutate the Sale.**
- The `idempotency_key` exists for symmetry with the other
  `receipts.*` handlers, but preview is effectively idempotent
  on `sale_id` — the same sale always previews to the same HTML
  (byte-stability per FR-016).

### `receipts.print` (internal — main-process only)

**Not directly callable from the renderer.** Fires automatically
from the print pipeline after AD-2 finalize completes (Slice 3).

The contract is recorded here for completeness; the renderer does
not import this handler from `bridge-api.ts`.

```text
(Internal main-process invocation; not part of the renderer bridge.)
```

### `receipts.reprint`

Reprint a previously-printed sale. Cashier-permitted per AD-10.

```text
Request:
  { sale_id: string,
    idempotency_key: string }

Response (success):
  { kind: 'ok',
    print_event_id: string,
    duplicate_copy_sequence_number: number,
    reprinted_at: string,              // ISO-8601 UTC
    render_path: 'escpos_direct' | 'os_print'
  }

Response (refused):
  { kind: 'refused',
    reason: 'no_session' | 'role_denied' | 'tenant_isolation' |
            'sale_not_found' | 'not_yet_printed' |
            'idempotency_payload_mismatch' | 'printer_unavailable' }
```

**Notes.**

- **Precondition** (per data-model Invariant 3 on PrintEvent):
  the sale MUST have at least one prior PrintEvent with
  `(purpose='first_print' OR purpose='retry_after_failure') AND
  outcome='success'`. Refused with `reason='not_yet_printed'`
  otherwise.
- **Drawer suppression** (per FR-030 / AD-8): a reprint MUST
  NOT open the cash drawer. **No fresh DrawerEvent is emitted for
  a reprint** *(revised 2026-05-27 post-external-review R2 — original
  prose claimed a `suppression_reason='reprint'` DrawerEvent was
  emitted; that branch was unreachable because the `UNIQUE (sale_id)`
  constraint on `drawer_events` blocks any second INSERT)*. The
  audit trail for "reprint considered drawer-kick" is captured by
  the `sale.receipt.reprinted` audit event combined with the
  absence of a fresh DrawerEvent row.
- **Duplicate-copy marker** (per FR-029 / AD-6): the
  `reprint_duplicate` template variant is used; the bilingual
  marker is rendered prominently.
- **Attribution** (per FR-024 / AD-10): the bridge handler uses
  the *current* signed-in operator's identity (the **reprinting**
  operator), not the selling operator id from the Sale row. Both
  are present in the audit log.

### `receipts.retryPrint`

Retry a failed print. Used by the persistent printer-failure
banner.

```text
Request:
  { sale_id: string,
    idempotency_key: string }

Response (success):
  { kind: 'ok',
    print_event_id: string,
    purpose: 'retry_after_failure',
    outcome: 'success',
    render_path: 'escpos_direct' | 'os_print',
    printed_at: string }

Response (refused):
  { kind: 'refused', reason: <one of the enum above> }

Response (still-failed):
  { kind: 'ok',
    print_event_id: string,
    purpose: 'retry_after_failure',
    outcome: 'failure',
    failure_reason: 'printer_offline' | 'printer_out_of_paper' |
                    'printer_jam' | 'os_print_error' |
                    'escpos_write_failure' | 'escpos_status_unknown' }
```

**Notes.**

- A successful retry MUST be treated as the canonical first print
  per FR-052: no duplicate-copy marker; drawer-kick eligible on a
  cash-inclusive sale (FR-053 still suppresses double-kick).
- A still-failed retry returns `kind:'ok'` with `outcome:'failure'`
  (not `kind:'refused'`) because the retry attempt itself was
  *accepted* — it ran and got a failure ack back. The banner
  remains persistent.

### `receipts.manualOverride`

Cashier invokes manual-receipt override after a print failure.
Used by the persistent printer-failure banner.

```text
Request:
  { sale_id: string,
    idempotency_key: string }

Response (success):
  { kind: 'ok',
    print_event_id: string,
    purpose: 'first_print',
    outcome: 'manual_override',
    overridden_at: string }

Response (refused):
  { kind: 'refused', reason: <one of the enum above> }
```

**Notes.**

- The audit event is `sale.receipt.manual_override`.
- **Edge case** (per spec Edge Cases): a sale that took
  manual-override but later has a successful retry-print is
  treated as "first print after manual override" — the next
  `receipts.retryPrint` succeeds with
  `purpose='retry_after_failure' AND outcome='success'`, NOT
  as a reprint. The duplicate-copy marker is absent on this
  slip.
- The banner is dismissed by the renderer once `manualOverride`
  returns success. The cashier can still invoke
  `receipts.retryPrint` later if the printer comes back online.

## Sensitive-data minimisation (load-bearing on this contract)

This contract is the **bridge surface**, and it is where
Constitution §P6 (no cardholder data), §P7 (no secrets to
renderer), and the spec §"Sensitive-data minimisation"
(FR-070–FR-074) are enforced.

The handlers above are **listed** as the entire 008 bridge
surface; no other 008 handlers exist. By construction, the
following fields **CANNOT** cross the bridge to the renderer:

- PAN, CVV, track data, cardholder name, expiry, auth payload,
  approval code, terminal receipt text, cryptograms.
- Voucher code, voucher balance, voucher holder PII, voucher
  redemption intent token, raw voucher authority payload.
- Cashier PIN, PIN hash, password, JWT, device token, attestation.
- Raw `PaymentIntentEnvelope v1` payload.
- Full receipt payload (only the HTML rendering crosses, and only
  via `receipts.preview` — the underlying bytes-form is main-only).
- `tenant_tax_registration_id`, `envelope_handoff_action_id`,
  `payment_attempt_id` (these are main-process / audit-layer fields
  excluded from the `sales.read` response).

The `external_reference` field crosses to the renderer ONLY when
006 OQ-PLAN-5 resolves permissively AND only inside the
`tender_lines_summary` array of `sales.read` (6-character
alphanumeric per 006 FR-009 — cannot encode card data by
construction). The `voucher_authority_redemption_id` crosses to
the renderer ONLY when 006 FR-017 / OQ-PLAN-7 resolves
permissively (non-sensitive identifier per 006 FR-017).

A defensive forbidden-field check runs main-side at every bridge
handler entry (the same key list as data-model.md §"Forbidden
fields"). Detection → `reason='forbidden_field_in_request'`,
audit event emitted.

## §A4 security-review checklist (handed off at Slice 1 commission)

The §A4 reviewer MUST verify the following, in order:

1. **Bridge surface enumeration.** Confirm that the four
   `receipts.*` handlers + three `sales.*` handlers above are the
   entire 008 bridge surface. No `drawer.*` renderer-callable
   surface.
2. **Forbidden-field defensive guard.** Confirm the main-side
   guard at every bridge handler entry rejects any of the
   forbidden keys in the request payload.
3. **Refusal-envelope shape.** Confirm every refused response
   uses `{ kind: 'refused', reason: <closed enum> }` and the
   `reason` enum is closed (no free-form strings).
4. **Idempotency contract.** Confirm `idempotency_key` is
   accepted by every mutating handler and is the load-bearing
   replay-detection mechanism (mirrors 005 / 006).
5. **Operator-attribution discipline.** Confirm `receipts.reprint`
   uses the current signed-in operator's identity (the reprinting
   operator), not the selling operator id from the Sale row.
6. **Tenant isolation.** Confirm every handler scopes by
   `tenant_id` + `branch_id` + `terminal_id` from the session;
   `sales.findByNumber` is the most-likely vector for cross-
   tenant probing and MUST refuse with `sale_not_found`, not
   `tenant_isolation`, on cross-tenant misses (no information
   leak).
7. **Redaction surface.** Confirm `external_reference` is
   `*****`-redacted in every log sink the bridge writes to
   (pino, Sentry, support bundle), regardless of which handler
   processed it.
8. **No raw envelope leak.** Confirm no bridge response includes
   the `envelope_handoff_action_id` (it lives main-side only as
   the audit / idempotency anchor).
