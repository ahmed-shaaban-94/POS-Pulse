# Contract — `POST /api/v1/terminals/pair`

This is the planning-time snapshot of the HTTP contract this feature consumes. The runtime types
live in `src/shared/api-types.ts`, regenerated by `npm run codegen:api` from the refreshed
`scripts/openapi-snapshot.json`. The shape below MUST match what the snapshot publishes; any
divergence is a CI failure (`codegen:verify`) and a backend-side coordination point.

## Purpose

The single backend call where `X-Terminal-Token` is **absent**. Exchanges a short-lived,
one-shot pairing code for a long-lived device token plus the bound assignment tuple.

## Request

| Field | Type | Required | Notes |
|:--|:--|:--|:--|
| Method | `POST` | yes | |
| Path | `/api/v1/terminals/pair` | yes | Mounted under `${VITE_API_BASE_URL}` |
| Headers — `Authorization` | absent | n/a | This endpoint is unauthenticated user-side; the pairing code is the sole credential. |
| Headers — `X-Terminal-Token` | absent | n/a | This is the only call where the device token does not yet exist. |
| Headers — `Content-Type` | `application/json` | yes | |
| Body — `pairing_code` | `string` | yes | Server-defined format and length; client does not validate. Treated as a secret. |

## Successful response — `200 OK`

```jsonc
{
  "device_token":   "<opaque-string>",     // SECRET; stored only via SecretStore.
  "tenant_id":      "<id-string>",         // Configuration.
  "branch_id":      "<id-string>",         // Configuration.
  "terminal_id":    "<id-string>",         // Configuration.
  "terminal_label": "<human-readable>",    // Display only.
  "expires_at":     "<ISO-8601 | null>"    // OPTIONAL; this feature ignores it (see data-model.md).
}
```

The device token MUST be stored exclusively via the `SecretStore` abstraction from 001. The
remaining four fields populate the single-row `terminal_assignment` table. `expires_at`, even if
present, MUST be ignored by this feature.

## Failure responses

The backend MUST emit one of the typed envelopes below. Any other shape is treated as
`UNKNOWN_ERROR` by the client (defensive default — not a substitute for the contract).

| HTTP status | `body.code` | Meaning | Client outcome | UI message family |
|:--|:--|:--|:--|:--|
| `400` | `"INVALID_CODE"` | Code is not recognised. | `INVALID_CODE` | "Code not recognised — check and try again." |
| `410` | `"EXPIRED_CODE"` | Code is past its TTL. | `EXPIRED_CODE` | "Code expired — generate a new one." |
| `409` | `"ALREADY_PAIRED"` | Code has been consumed. | `ALREADY_PAIRED` | "This code has already been used." |
| `409` | `"BRANCH_MISMATCH"` | Terminal is registered to a different branch. | `BRANCH_MISMATCH` | "Terminal registered to another branch — ask admin to release it." |
| `429` | `"RATE_LIMITED"` | Too many pair attempts. | `RATE_LIMITED` (with `retry_after_s`) | "Too many attempts — wait a moment." |
| `5xx` | any | Backend transient. | `UNKNOWN_ERROR` | "Pairing failed — try again later." |
| (no response) | n/a | Network unreachable / DNS / TLS fail. | `NETWORK_ERROR` | "No connection — check the network." |

### Error envelope shape

```jsonc
{
  "code":    "INVALID_CODE" | "EXPIRED_CODE" | "ALREADY_PAIRED" | "BRANCH_MISMATCH" | "RATE_LIMITED",
  "message": "<human-readable>"   // Logged but never shown to the operator verbatim — UI uses its own message family for consistency.
}
```

### `Retry-After` header (only on `429 RATE_LIMITED`)

- Value MAY be either a `delta-seconds` integer or an HTTP-date.
- Client clamps the parsed wait to **`[1 s, 300 s]`** before disabling submit.
- Failed parses default to `30 s`.

## Idempotency

A pairing code is one-shot. The terminal MUST NOT retry a code that the backend has accepted. The
terminal MUST NOT retry a code that the backend has rejected as `INVALID_CODE`, `EXPIRED_CODE`, or
`ALREADY_PAIRED`. For `BRANCH_MISMATCH`, retrying is also pointless (admin must release the
terminal first); the UI does not auto-retry.

## Security and observability

- The request body's `pairing_code` MUST NOT appear in any log line, Sentry event, or telemetry
  payload at any level. The `network.ts` module constructs the body in-place and does not pass
  the request object to the logger.
- The response's `device_token` MUST NOT appear in any log line, Sentry event, or telemetry
  payload at any level. The pairing service writes it to the SecretStore directly without
  re-emitting it through any logger boundary.
- The Sentry breadcrumb (if DSN is configured) MUST contain only the outcome category and the
  HTTP status; the request body, response body, and any error message that quotes them are
  filtered out by the existing 001 scrubber, extended in this feature with the two key names.
