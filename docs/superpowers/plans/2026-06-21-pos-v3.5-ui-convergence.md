# POS v3.5 UI Convergence — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Converge the real engine-backed POS-Pulse terminal onto the v3.5 design prototype, screen by screen, keeping the engine intact and fixing internal defects test-first along the way.

**Architecture:** Incremental, primitives-first (Approach A+ from the design spec). Phase 0 reconciles tokens/primitive class vocabulary; Phase 1 recomposes the live money/audit screens; Phase 2 builds out the stub screens. Each screen is one slice = one PR. The visual layer binds to existing Zustand stores + the `window.api` IPC bridge; primitive prop APIs are frozen.

**Tech Stack:** Electron 40, React 19, Tailwind 4, Zustand, Vitest, TypeScript. Reference prototype: `docs/design/pos-v3.5/` (`pos-app.jsx`, `kit.css`).

**Spec:** `docs/superpowers/specs/2026-06-21-pos-v3.5-ui-convergence-design.md`

**Verification commands (this repo):**
- Tests: `npm test` (`vitest run --passWithNoTests`)
- Types: `npm run typecheck`
- Lint: `npm run lint` (`eslint . && prettier --check .`)

**Commit/PR rule (non-negotiable):** Stage only specific named files (never `git add -A`/`.`). No commit, push, PR, or merge without explicit per-action owner approval. Stop and report at each commit boundary.

---

## Scope of THIS plan

This plan is **complete and executable for Phase 0 + the first live slice (Slice 1: Shell + sign-in + open-shift)**. The remaining 12 screens each instantiate the **Per-Slice Template** (end of this doc) and will be expanded into their own full task lists once Slice 1 has executed and informed the pattern. This avoids speculative planning: the first slice will reveal how cleanly hook-extraction and class-mapping go.

**Slice order (from spec §5):**
- Phase 0 — token/primitive reconciliation (Tasks 1–3 below)
- Phase 1 (live, money/audit first): **Slice 1** Shell + sign-in + open-shift *(planned in full below)* → Slice 2 Catalogue/sale pane → Slice 3 Cart pane → Slice 4 Tender/payment surface
- Phase 2 (stubs): Slice 5 Dashboard → 6 Sales history → 7 Returns → 8 Audit → 9 Inventory → 10 Settings → 11 Close-shift/Z-report → 12 Customer display

## Per-Slice Template (Slices 2–12)

Each remaining screen instantiates this loop (expanded into full tasks when its slice begins, after
Slice 1 informs the pattern). The screen's prototype reference is in `pos-app.jsx` per the spec inventory.

1. **Per-screen defect audit** — read the screen's current surface (or confirm it's a stub) + the
   engine it binds to. Log defects (internal vs contract) in the register.
2. **Confirm engine contract** — `grep` the bound store + bridge methods. If the screen needs data
   the engine can't supply → **escalate as a contract decision; STOP at the boundary.**
3. **Write failing test(s)** for the prototype's layout/copy/behavior (exact strings from `pos-app.jsx`).
4. **Run → verify fail.**
5. **Recompose (live) or build out (stub)** the screen, reusing frozen primitives, binding to engine.
6. **Fix internal defects test-first** as encountered.
7. **Run `npm test && npm run typecheck && npm run lint` → verify green.**
8. **Visual check** vs `POS-Terminal-prototype.html`.
9. **Commit named files; STOP for owner approval; one PR per slice.**
