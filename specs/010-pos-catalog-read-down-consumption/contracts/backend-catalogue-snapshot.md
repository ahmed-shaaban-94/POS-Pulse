**Feature ID:** 010-pos-catalog-read-down-consumption
**Plan:** [../plan.md](../plan.md) (R3, R6)
**Status:** 🚧 **PROPOSED — NOT a committed local contract.** This is a *request to the SmartDataPulse
backend team* for a catalogue-snapshot operation. It is the **implementation blocker** for 010.
**Created:** 2026-06-04
**Constitution version pinned:** v1.5.1

---

## Why this is PROPOSED, not final

`src/shared/api-types.ts` (generated by `openapi-typescript` from the backend OpenAPI snapshot) currently
exposes **no `/products/*` catalogue-snapshot operation** (verified 2026-06-04 — only operator, shift,
voucher, dispensing, analytics operations exist). Constitution **Principle V** requires backend types be
**generated, never hand-typed**. Therefore:

- **This contract is a proposal to the backend** for the operation it must publish.
- 010 implementation is **blocked** until either (a) the backend publishes the OpenAPI operation and
  `npm run codegen:api` regenerates `src/shared/api-types.ts` (a codegen-owned/forbidden-scope file — a
  further reason implementation is gated), or (b) an explicit, time-boxed **Constitution V waiver** is
  filed for a temporary hand-typed shape with an expiry condition.
- No local code consumes this shape until it lands in `api-types.ts` as
  `components['schemas']['…']` (the same way the voucher clients consume their generated types).

## Proposed operation

```text
GET /api/pos/v1/products/catalogue            (or POST /api/pos/v1/products/snapshot)
  — returns the FULL current sellable-product catalogue for the requesting terminal's
    tenant (and branch, where branch-scoped). Full-snapshot replace model (R3).
```

**Terminal authentication — `X-Terminal-Token` header (constitution-mandated).** The device token rides
the **`X-Terminal-Token`** request header, per Platform Integration §Auth (`constitution.md:955-960`):
every backend request carries `Authorization` + `X-Terminal-Token`. `src/main/index.ts:121` names this
exact header for "any future feature that reads the token." The token is read from
`secretStore.get(DEVICE_TOKEN_KEY)` in the main process; it is a secret — attached to the outbound request
only, **never** crossing the bridge to the renderer or entering a log (P7; `device_token` already on the
forbidden-keys allowlist).
> **Corrected 2026-06-04 (review finding):** an earlier draft proposed a request-body attestation field
> and claimed "no `X-Terminal-Token` header exists." That was wrong — `device_token_attestation` is 004's
> *sign-in-specific* signed body field (sent alongside a JWT), not the general per-request terminal-auth
> mechanism. The constitutional `X-Terminal-Token` header is controlling.

**Operator JWT.** Not required for the read-down — it runs on a paired terminal without an operator
session (R8 / Constitution VIII background-sync allowance), so `X-Terminal-Token` is the **sole** auth
credential on the request. **Backend confirmation needed (§A6):** that the snapshot endpoint accepts
`X-Terminal-Token` without an `Authorization` JWT for this read-only background call. The token's claims
(`tenant_id, branch_id, terminal_id`) scope the returned snapshot.

## Proposed response shape (illustrative — for backend negotiation)

Each product record MUST carry everything 009's read model requires (009 `data-model.md`):

```text
CatalogueSnapshotResponse {
  snapshot_id: string                 // opaque provenance id → catalogue_sync_state.source_snapshot_id
  tenant_id: string                   // MUST match the terminal's tenant (P17 guard)
  branch_id?: string
  products: Array<{
    product_id: string                // stable identity
    sku: string
    name_ar: string                   // required (Arabic-first)
    name_en?: string
    aliases?: string[]
    price_minor: integer              // integer minor units; safe-integer; ≥ 0 (P1)
    tax_category: string
    unit_pack_label?: string
    active: boolean
    controlled_substance: boolean
    prescription_required: boolean
    row_version: string               // per-product change marker (009 R9 provenance)
    created_at: string                // ISO-8601 UTC
    updated_at: string
    barcodes: Array<{
      barcode: string                 // EAN/GTIN
      barcode_kind?: 'pack' | 'unit'
    }>
  }>
}
```

**Note — fold columns are NOT in the contract.** `name_fold` / `alias_fold` / `sku_norm` /
`barcode_norm` are **computed locally** by 010 with 009's `normalize()` (R1); the backend MUST NOT be
relied on to supply them (FR-3 / SC-9).

## Client behaviour (committed locally, independent of the shape)

The read-down HTTP client follows the established repo pattern (`operator/backend-client.ts`, the
voucher-authority clients):

- Factory `{ baseUrl, fetch, timeoutMs }`; `fetch` injected (prod binds `globalThis.fetch`).
- `AbortSignal.timeout(timeoutMs)`.
- **Resolve on every reachable response (incl. non-2xx); reject only on transport failure** → typed
  discriminated outcome with a `no_connection`-style sentinel.
- Non-2xx / malformed body → a typed `failed` outcome (FR-7: prior catalogue preserved).
- **Raw response body is never logged** (R7 / NFR-3).

## Open items for backend coordination (the implementation gate)

1. Endpoint, verb, and whether snapshot is paginated/streamed for large catalogues (chunked staging is
   an implementation option if so).
2. Confirm the endpoint accepts the **`X-Terminal-Token` header without an `Authorization` JWT** for this
   read-only background call (the auth *header* is constitution-fixed; only the JWT-absent acceptance for
   a terminal-only call needs backend confirmation).
3. Publishing the OpenAPI operation so `api-types.ts` regenerates (Constitution V).
4. Tenant/branch scoping semantics of the snapshot.
