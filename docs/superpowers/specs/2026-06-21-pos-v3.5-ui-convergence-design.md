# POS v3.5 UI Convergence — Design

- **Date:** 2026-06-21
- **Status:** Design — awaiting approval (no implementation started)
- **Repo:** POS-Pulse (Electron 40 + React 19 + Tailwind 4)
- **Reference handoff:** `docs/design/pos-v3.5/` (vendored 2026-06-21)
- **Architecture boundary owner:** Retail Tower Orchestrator

---

## 1. Goal

Make the **real, engine-backed POS-Pulse terminal** look and behave **pixel-faithfully like the
v3.5 design prototype**, screen for screen, while keeping the existing engine (stores, IPC bridge,
money math, audit) as the source of behavior.

The prototype is a **specification, not the product.** Its own handoff says: *"They are not
production code to paste in. Your job is to recreate this terminal in the target codebase's
environment."* The prototype runs on fake data and has no engine; it cannot take a real payment,
sync a sale, or write an audit record. We are not shipping the prototype — we are converging the
real app onto its appearance and behavior.

### End state

| | Prototype (kept in `docs/design/pos-v3.5/`) | End-state POS-Pulse app |
|---|---|---|
| Looks like | v3.5 design | **Identical** to v3.5 design |
| Data | Fake mock arrays | Real catalogue / cart / operators |
| Payments | Simulated math | Real tender via IPC → Data-Pulse-2 contracts |
| Sales | Nothing persists | Persist locally; sync online; queue offline |
| Audit | Fake array | Real records, attributable to operator |
| Role | Reference / answer key (stays) | The shipping terminal |

The prototype stays in-repo as the **reference we measure against** — never deleted, never the app.

The repo is **not** a finished UI being thrown away. It is a partially-built terminal whose design
system **already aligns** with the v3.5 handoff:

- **Live screens** (real engine bindings today): sign-in, shell, catalogue sale pane
  (`CatalogueSalePane`), cart pane (`CartPane`), payment surface (`PaymentSurface`),
  receipts banners.
- **Stub screens** (`*Placeholder.tsx` today): dashboard, sales, inventory, settings — and several
  prototype screens have no surface yet (returns, audit, close-shift/Z-report, customer display,
  open-shift).

  `operator-session-store`, `catalogue-search-store`, `feature-flags-store`, `theme-store`); IPC
  bridge `window.api` (`pairing`, `operator`, `cart`, `catalogue`, `payments`, `tender`, `sales`,

**Implication:** This is a **convergence**, not a from-scratch rebuild. The bones already match the
handoff. What diverges is screen-level composition and the fact that many screens are still stubs.

## 4. Architecture & boundaries

```
VISUAL  (replace / build) ── screens, layout, composition, copy, screen-level styling
   │  binds to
PRIMITIVE (reuse, restyle only) ── Button/Badge/Card/Dialog/Input/Table/StatusBanner/Toast,
   │                               PinPad, NavRail, TopBar, OperatorBadge, ConnectionIndicator,
   │                               AmountPad, MoneyRoll, state components
   │  binds to
ENGINE  (KEEP — contract boundary) ── stores (FSMs), window.api IPC bridge, money-math,
                                        audit emit, theme persistence, connection state
```

**Rules (non-negotiable):**

- Primitive **public APIs (props) stay identical.** Restyle internals only; do not change a
  primitive's prop surface, because every consumer + its tests depend on it.
- Visual layer **binds to the engine through existing stores + the `window.api` bridge.** No new
  bridge methods, no new store fields, without escalation (§6).
- **PinPad security model is preserved** — PIN never rendered as text; dot-only feedback; no
  `aria-live` timing leak. Any restyle keeps these invariants and its existing tests green.
- **Money is minor units (piasters), integer arithmetic, 14% VAT on `vatable:true` lines only.**
  Display formatting may change; arithmetic does not move into the visual layer.
- **No business/catalog/inventory/sales data path other than Data-Pulse-2** (program architecture
  boundary). UI binds to what the engine already supplies.

## 5. Approach — Incremental, primitives-first, per-slice defect gate (Approach A+)

Chosen over (B) "restyle-everything-at-once" — too broad a regression surface for money/audit
screens — and (C) "parallel flagged rebuild" — duplicates engine bindings for no gain since the
design system already aligns.

### Phase 0 — Token / primitive reconciliation
Align existing primitives + `tailwind.css` class vocabulary to the prototype's `kit.css` names
(`.cart-pane__*`, `.tender-slots`, `.method-card`, `.account-row`, `.amount-pad__*`, etc.) where
they diverge. Small, high-leverage, every screen benefits. Primitive prop APIs unchanged.

### Phase 1 — Live screens, most-careful-first
One screen per slice, in this order (money/audit screens first, treated most carefully):
1. Shell + sign-in + open-shift
2. Catalogue / sale pane
3. Cart pane (line items, qty, hold, void, Rx gate, interaction warnings)
4. Tender / payment surface (cash, card, voucher, credit, insurance co-pay)

### Phase 2 — Stub screens, build-out
One screen per slice: dashboard → sales history → returns → audit → inventory → settings →
close-shift / Z-report → customer-facing display.

### Per-slice loop (every screen)
1. **Per-screen defect audit** — focused review of the screen + the engine slice it binds to,
   *before* rebuilding. Catalogue defects with evidence + severity.
2. **Tests** — keep existing tests green; write tests for new screen behavior (TDD: red → green).
3. **Recompose / build** the screen against the prototype, binding to existing engine.
4. **Fix internal defects test-first** (§6); escalate contract-level defects (§6).
5. **Verify** — `vitest run` green; visual check against the prototype screen.
6. **Slice = its own commit / PR** (matches POS-Pulse's numbered-PR culture). Stop for owner
   approval before any commit/push/PR/merge.

## 6. Defect-handling protocol (decided with owner 2026-06-21)

Defects **will** surface in both the old UI and the engine. Two kinds, two handlings:

- **Internal defect** — wrong behavior entirely inside POS-Pulse that does **not** change what
  crosses the wire to Data-Pulse-2 (e.g. a display bug, a local FSM mistake, a miscomputed on-screen
  total). → **Fix immediately, test-first:** write a failing test that proves the defect, fix it,
  confirm green, within the same slice. The test suite grows and the engine gets *more* trustworthy.
- **Contract defect** — wrong behavior caused by the Data-Pulse-2 contract itself (missing field,
  wrong agreed payload shape, behavior the contract doesn't permit). → **Do NOT fix unilaterally.**
  Log it, advance it to a decision record, and **STOP at the boundary for owner ratification.** This
  is the architecture-boundary gate; it is never bypassed.

**Defect hunt depth: per-screen audit** — each slice begins with a focused defect review scoped to
that screen + its bound engine surface. No giant upfront audit phase; no purely-opportunistic
"only what we trip over" either.

**Defect register:** `docs/design/pos-v3.5/defect-register.md` — every defect found, with: id,
screen/slice, description, evidence, severity, classification (internal | contract), and status
(open | fixed-with-test | escalated-awaiting-ratification).

## 7. Reversibility / backup (decided with owner 2026-06-21)

Before removing or heavily rewriting any live screen:

1. **Archive branch** `archive/ui-pre-v3.5` pointing at the pre-work `main` tip, plus a git tag, as
   a labeled restore point. (Git already preserves history; the branch/tag is a human bookmark.)
2. All convergence work happens on a **feature branch** (e.g. `feat/pos-v3.5-ui`), landing via
   per-slice PRs — never direct commits to `main`.
3. The vendored prototype in `docs/design/pos-v3.5/` is never deleted — it is the reference.

## 8. Testing strategy

- **Keep the ~15k-LOC suite green at every slice** — it is the regression net for the engine.
- **TDD for new screen behavior** — red → green → refactor, per the per-slice loop.
- **Per primitive restyle:** existing primitive tests must stay green (prop APIs unchanged).
- **PinPad / money / audit:** treated as security-critical — no slice merges with these tests red.
- Coverage target follows the repo's existing standard; new screens carry unit + interaction tests.

---

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Restyling a primitive breaks many consumers | Prop APIs frozen; only internals/CSS change; primitive tests gate each change |
| Money/audit regression on live screens | Live screens slice first, most carefully; money math stays in engine; tests gate |
| Composite components (CartPane, PaymentSurface, CatalogueSalePane) mix logic + view | Extract bridge/store interaction into hooks before reskinning; present clean props to new view |
| Scope sprawl across 13 screens | One screen per slice; each independently shippable; pause anytime |
| A screen needs data the engine can't supply | Escalate as contract decision (§6); do not invent a bridge method |
| Broad CSS change destabilizes everything | Rejected Approach B for this reason; Phase 0 token work is additive + class-scoped |
| Big visual change in long context window | Slices are small + isolated, keeping each change in the safe context zone |

## 11. Acceptance criteria (handoff ideal, reconciled to §12)

> **[deferred]** / **[blocked]** here so this checklist gates only what is actually in scope now.

- Dark default + light toggle (token overrides only); theme persists.
- Prototype routes reachable: sign-in, tender, receipt, customer display, dashboard, sales history,
  audit, inventory, settings. **Open/close shift = [deferred]** (UI-shell only, G2 — §12). **Returns
  = [blocked]** (Phase-7 — §12).
- Tender: **cash / external_card_terminal / internal_voucher only**, correct change/remainder math
  (minor units) — backed by the real engine. **Credit + insurance co-pay = [blocked]** (Phase-6
  parked — §12). **VAT = [deferred]** (tax-pending placeholder, no live 14% allocation asserted —
  ADR-0003 / §12).
- Rx/controlled **badge** present (display-only, non-blocking — catalogue contract). Interaction /
  expiry / stock honesty surfaces = **[deferred]** enrichment shells (need POS-013 DP-2 contract — §12 / D-005).

- One-Accent + Status-Color-Containment respected; no anti-pattern introduced.
- Every accountable action audit-logged via the real audit path; sales attributable to operator;
  offline → Queued. (Applies as each surface's real engine path lands.)

## 12. Reconciliation with the program roadmap (added 2026-06-21)

This convergence effort is **governed by** the orchestrator's pre-existing control-plane roadmap:
`Retail-Tower-Orchestrator/docs/roadmap/pos-v3-5-terminal-handoff-adoption-roadmap.md`
(Slice ID `ORCH-POS-V35-HANDOFF-ADOPTION-001`, dated 2026-06-18). That roadmap is the **authority**;
where this spec diverged, the roadmap wins. Reconciliation results:

**Aligned (no change):** reuse existing primitives; recreate-not-paste; DP-2 is the contract boundary
(STOP at G2 for any contract/payload/migration change); small independently-revertible slices;
dark-default + RTL + token parity.

**Slice↔Phase mapping:**

| This spec's slice | Roadmap phase | Gate posture |
|---|---|---|
| Phase 0 (tokens) + Slice 1 shell | **Phase 1** (visual shell / RTL / tokens) | G0 only — presentation; SAFE |
| Slice 1 sign-in | Phase 1 (sign-in is in §2 shell scope) | G0; binds live operator engine; SAFE |
| Slice 2 catalogue/sale pane | **Phase 2** (sale/cart/catalog) | G0; honesty surfaces only where data already exists; STOP at G2 otherwise |
| Slice 3 cart pane | Phase 2 | G0; no new sale fields |
| Slice 4 tender/payment | **Phase 3** | **SAFE TENDERS ONLY** — see correction below |
| Open-shift, dashboard, inventory, settings | **Phase 4** | UI-shell / existing-safe data only; **shift persistence deferred (G2)** |
| Receipts, sales history, audit | **Phase 5** | display polish only; audit invariants not modified |

**CORRECTIONS to this spec (roadmap overrides):**

1. **Tender — Slice 4 is SAFE TENDERS ONLY.** Only `cash`, `external_card_terminal`,
   `internal_voucher` may be wired as production behavior. The prototype's **`credit` (آجل) and
   `insurance` co-pay (تأمين) tiles are PARKED** (roadmap Phase 6, owner decision 2026-06-19; blocked
   on POS-020 + DP-2 035 settlement). They render as **not-wired** at most; no credit/insurance
   tender logic, co-pay math, or routing is implemented. This spec's §11 "cash/card/voucher/credit/
   insurance tender … co-pay math" criterion is **amended** to the three safe tenders only.

2. **Returns — BLOCKED, removed from buildable scope.** `ReturnsScreen` is roadmap **Phase 7
   (BLOCKED**, returns gate: POS-011 live + Connector reversal + DP-2 026). It is **removed** from
   this effort's stub-build list (was Slice 7). Not built until separately gated + approved.

3. **Tax/VAT — not asserted.** Per ADR-0003 (tax/fiscal PARKED), **no VAT allocation rule is
   asserted until production.** This spec's §11 "14% VAT on vatable lines" is **amended** to:
   VAT is a `tax-pending` placeholder; the UI must not assert a live VAT computation. Receipt/tax
   behavior is roadmap Phase 7 (BLOCKED).

4. **Open-shift persistence — G2 contract gap (D-003).** Verified 2026-06-21 against DP-2
   `origin/main`: a `pos-shifts` module exists but exposes only `GET /api/pos/v1/shifts/stuck`;
   there is **no `POST` open/start-shift operation** and no POS bridge method for it. Per roadmap
   Phase 4, open-shift is **UI-shell-only**; persistence is deferred and **STOPS at G2** for owner
   ratification. **Slice 1 is therefore redefined as sign-in + shell only** (both unblocked); the
   open-shift screen becomes a later UI-shell-only slice.

**Net effect on the slice plan:**
- Slice 1 = **shell + sign-in** (open-shift dropped).
- Slice 4 = **cash/card/voucher only**; credit/insurance tiles not-wired.
- Returns removed from scope (Phase 7 BLOCKED).
- VAT/tax not asserted in UI (tax-pending placeholder).
- Open-shift, dashboard, inventory, settings = UI-shell / existing-data only (Phase 4), shift
  persistence G2-deferred.

## 13. Enrichment runway (thin-now, rich-later)

This effort lands several screens as **honest shells** — full v3.5 visual fidelity (layout, copy,
polish) with "no data source yet" panels wherever the backing contract is gated. This is deliberate:
the shell is the placeholder the future data **fills into without re-layout**. Enrichment is a planned
follow-on pass over the *same* screens, not a rebuild.

**Three enrichment waves:**

1. **Within this convergence (Phases 1–5).** Full visual fidelity immediately; live data wired
   wherever it already exists (sign-in, cart, catalogue, safe tenders, receipts/history/audit display).
2. **Gate-unlock enrichment** — a screen built thin now becomes rich when its upstream DP-2 contract
   goes live AND the owner ratifies (the G2 boundary). Mapped below.
3. **Post-roadmap polish** — ordinary iterative refinement (motion, a11y, interaction tuning); no gate.

**Gate-unlock map — where each shell enriches:**

| Screen / feature | Lands now as | Enriches when… | Gate / ref |
|---|---|---|---|
| Dashboard metrics (today's sales, top items) | shell, "no data yet" | DP-2 dashboard-metrics contract live | POS-013 (deferred) |
| Inventory awareness (stock / expiry honesty surfaces) | shell / catalogue-read-down only | DP-2 POS-stock contract live | POS-013 (blocked) |
| Open-shift / close-shift / Z-report | UI-shell only (Slice 12) | DP-2 `POST /shifts` open-shift contract built | POS-015 / D-003 (G2) |
| Credit + insurance co-pay tenders | tiles **not-wired** | POS-020 + DP-2 035 settlement live | Phase 6 (PARKED) |
| Returns / refund slip | **not built** | returns gate (POS-011 live + Connector reversal + DP-2 026) | Phase 7 (BLOCKED) |
| Live VAT / tax on receipts | `tax-pending` placeholder | tax/fiscal gate (G6) un-parks | Phase 7 / ADR-0003 |

**Hard rule for every row:** enrichment requiring **new DP-2 data** is gated on a contract owned
upstream and an explicit owner ratification. We **build the shells** so enrichment is a fill-in; we do
**not** author the DP-2 contracts. Each unlock is a fresh, separately-approved follow-on slice against
the shell this effort produces.
