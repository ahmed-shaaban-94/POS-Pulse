# Phase 1 Data Model — Cashier-PIN Provisioning (019)

## Entity: CashierPinRecord (existing — extended, not redefined)

`cashier_pin_records` (migration `0006`). 019 adds the **create** path and one **additive column**; it does not redefine the entity. Full schema after 019's additive column:

| Field | Type | 019 change | Notes |
|:--|:--|:--|:--|
| `tenant_id` | TEXT NOT NULL | — | PR-4 scope; from pairing state. |
| `branch_id` | TEXT NOT NULL | — | PR-4 scope. |
| `terminal_id` | TEXT NOT NULL | — | PR-4 scope. |
| `cashier_clerk_user_id` | TEXT NOT NULL | — (bridge) | Current PK component (provider-coupled). 017 demotes to nullable bridge; 019 still populates it during the bridge window for legacy correlation. |
| **`user_id`** | **TEXT (nullable)** | **ADDED (R-1)** | **The provider-neutral identity key (028 §16 = DP-2 `users.id`). 019-created rows ALWAYS populate it; legacy rows NULL until 017 backfills. Non-key in 019; 017 promotes it into the PK.** |
| `pin_hash` | BLOB NOT NULL | — | Argon2id PHC bytes; sealed. Generated by `hashPin`, sealed by `sealPinMaterial`. Never plaintext, never off-device. |
| `pin_salt` | BLOB NOT NULL | — | Per-record salt; sealed. |
| `failed_attempt_count` | INTEGER NOT NULL DEFAULT 0 | — | Starts 0 on provision. |
| `lockout_until` | TEXT (nullable) | — | NULL on provision (not locked). |
| `created_at` | TEXT NOT NULL | written | Provision timestamp. |
| `created_by_operator_id` | TEXT NOT NULL | written | The provisioning manager/admin (P10). |

**PK during 019:** unchanged — `(tenant_id, branch_id, terminal_id, cashier_clerk_user_id)`. (017 re-keys onto `user_id`.) 019 writes BOTH `cashier_clerk_user_id` (current PK) AND `user_id` (born-neutral), so the row is keyed correctly today and ready for 017's re-key.

> **Why 019 writes both keys:** the PK column is still `cashier_clerk_user_id` until 017's rebuild, so 019 must populate it to satisfy the constraint. But 019 ALSO populates `user_id` so that when 017 re-keys, the row already has its neutral key — 017 never has to backfill a 019-created row (SC-2). 019-created rows are "born ready for the re-key".

## State transitions (provisioning)

```
[no row for (scope, cashier)]
        │  manager/admin provisions, roster carries user_id
        ▼
[row created: user_id populated, clerk_user_id populated, hash+salt sealed,
 failed=0, lockout=null]  ──── audit: cashier.pin.provisioned ────►
        │
        │  (later) reset path changes the secret  ──► hash/salt replaced, lockout cleared
        │  (later) 017 migration re-keys PK onto user_id  ──► clerk_user_id → bridge
```

**Refusal states (no transition, no row):**
- active operator not manager/admin → `refused: role_mismatch`
- terminal not paired → `refused: invalid_input`
- PIN shape invalid → `refused: invalid_input`
- roster entry has no `user_id` → `refused: not_ready` (FR-11)
- a row already exists for `(scope, cashier)` incl. legacy clerk-keyed → `refused: state_invalid` (FR-5; directs to reset)

## Validation rules

- PIN: same `^\d{4,6}$` policy as reset (Assumption; not redefined here).
- `user_id`: non-empty string required to create; absence → `not_ready` refusal.
- Scope (`tenant/branch/terminal`): all non-empty, from pairing state (never renderer).
- Create-only: existence check matches on `(tenant, branch, terminal, cashier)` across BOTH key columns (a legacy clerk-keyed row OR a neutral-keyed row counts as existing).
