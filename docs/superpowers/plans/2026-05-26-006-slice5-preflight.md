## (b) FSM transitions + idempotency-replay protections

### PaymentAttempt FSM (`src/main/payments/fsm/payment-attempt-fsm.ts`)

States: `started → settled | cancelled | failed | force_failed`. Once in a terminal state, ALL further transitions refused.

Transition table:
- `start` → `started` (insertion only)
- `started → settled` via `confirm()`
- `started → cancelled` via `cancel()`
- `started → failed` via `fail()`
- `started → force_failed` via `forceFail()` (manager only, FR-021, dual attribution)

### TenderLine FSM (`src/main/payments/fsm/tender-line-fsm.ts`)

States: `applied → reversed | reversal_pending → reversed`. Voucher-specific path: `reversal_pending` is set when V-A `vouchers.reverse` returns `authority_unreachable`; the deferred-reversal resolver later transitions to `reversed`.

### Idempotency-replay (`src/main/payments/idempotency.ts`)

Per Constitution §P5: every action authored by the renderer carries an `idempotency_key`. The handler hashes the request payload (with PII/PAN/external_reference redacted), and the outbox enforces `UNIQUE(action_id)` so a same-key replay returns the prior outcome from the outbox rather than re-applying the transition.

CR-3 defence-in-depth (Wave 4): the compensating-reverse path covers multi-voucher partial-redemption rollback. If `redeemVoucher` succeeds for line A and `authority_unreachable` for line B, line A is `reverseVoucher`'d at V-A then transitioned to `reversed`; if compensating-reverse itself returns `authority_unreachable`, line A goes to `reversal_pending` and the resolver handles it.
